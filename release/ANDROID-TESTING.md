# Physical Android APK/AAB test protocol

**Not executed by this setup.** Follow the existing `qa/STRATEGY.md`, manual case matrix and independent tester/reviewer evidence requirements. Use a passenger/parked operator; the driver must not operate forms while moving. No camera-evasion tests or sudden braking.

1. Download the identified development APK from Expo. Compare SHA-256 with the build manifest (`Get-FileHash -Algorithm SHA256 app.apk` in PowerShell; `sha256sum app.apk` on Linux). Inspect `apkanalyzer manifest application-id app.apk`, `apkanalyzer manifest version-code app.apk` and `apksigner verify --print-certs app.apk`. Record package, actual version code, minimum SDK, signer and hash. Avoid screenshots/logs containing real tokens, email codes or precise personal travel history.
2. Enable USB debugging only on an owned test device. Run `adb devices`, then `adb install -r app.apk`. If the certificate differs, stop and investigate; do not uninstall a user's app to bypass signature checks. A deliberate clean-install test must account for lost local data. `.dev` and `.preview` apps are separate installations.
3. Development APK: start the backend/database, run `npm run start --workspace @rova/mobile -- --dev-client --tunnel`, and scan the current development-client QR. Verify a harmless JS edit refreshes. This depends on Metro/network availability and is not standalone/offline acceptance. Native modules/config changes require a new APK.
4. Standalone preview APK: turn off Metro and verify cold start, branded icon/splash, guest navigation, permission denial/regrant and back/navigation-system insets. Test actual provider URLs configured for that environment; record missing or disabled features honestly.
5. On at least three physical Android devices including a low-memory model, execute GPS drift, poor/old fixes, wrong direction, parallel roads, rerouting, speed-limit unknown/transition behaviour, voice cooldowns/mute/priority, keyboard suggestions, reports/moderation freshness, airplane mode, flaky2G/3G/4G, background/return, battery/heat and failed-provider cases. Unknown/unverified data must never become a known limit or confirmed camera.
6. Test plaintext-to-encrypted migration using an identified previous APK on a controlled test account/device. Verify saved Home/Work/history preservation, opt-out, interrupted write, locked-keystore behaviour and erasure with a failed online notification cleanup. Test account/data deletion and queued external deletion honestly. Do not claim OS backups/forensic copies were wiped by app deletion.
7. AABs cannot be installed with `adb install`. For production delivery, upload the identified AAB to the **Play internal testing track**, opt in with a tester account and install from Play. Verify the Play app-signing certificate, splits, min/target SDK compatibility and real permissions; an APK signed with the upload key is not an equivalent Play-signing test. If using bundletool locally, use a checksum-pinned official release and a separate test signer, produce/install an APK set for that device, and label that result as a local split test rather than Play delivery evidence. Never put signer passwords on a public command line or in Git.
8. Repeat critical checks on the exact internal-track release candidate. Test a signed update over the previous supported version with saved places/preferences intact, and a clean install. Check final merged Android manifest permissions, unexpected SDK components, background location, exported components and telemetry, not just Expo config. Capture real screenshots (with consent), network evidence, Android vitals/crash/ANR observations and device metadata.
9. Attach artifact hashes and observations to the existing field-evidence template. Mark unexecuted/failed cases accordingly. Obtain independent safety, privacy/security, operations and product sign-offs. `qa:release` checks source identity and evidence; never fill approval fields with fictional reviewers. A changed native config/SDK/commit invalidates earlier candidate acceptance.

For public release ensure the backend is permanently hosted and reachable; a phone build does not host the TypeScript API or PostGIS database, and a development PC/tunnel is not production infrastructure.
