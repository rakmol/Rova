# Release ownership and rollout

Status: **not approved for public release**. Creating a signed AAB is not a release approval. No automated Play upload or publishing credential is configured.

1. Freeze a reviewed source commit and dependency lock. Green CI must include clean installation, secret scan, dependency audit and real integration checks. Archive native build metadata/hash and review [candidate release notes](notes/0.1.0.md).
2. Complete English human copy/pronunciation review, source/licensing/TraffiTech wording/legal determinations, production API/database hosting and verified TLS, monitoring/incident response, rate/cost controls and reviewed privacy/deletion URLs. Current local-PC services cannot be the launch backend.
3. Create a Play app as `gh.rova.mobile`, configure Play App Signing, verify account identity and restricted release permissions, and complete app-access/Data safety/permission/listing requirements. Check current Console SDK/native-library acceptance rather than guessing target/API compliance.
4. Install/test the exact AAB through the internal track; collect physical-device/road evidence and independent sign-offs. New personal developer accounts covered by Google's policy currently require at least12 continuously opted-in closed testers for14 days before applying for production access. Internal testing alone is not that closed-test requirement; eligibility and approval must be confirmed in the actual account.
5. Run `npm run qa:release -- <automated.json> <field.json>` against current complete, hashed artifacts. No missing/failed/expired case or critical/high defect may be marked passed. A release owner must explicitly approve public publication. Store policy/privacy/provider and field approval remain separate from CI success.
6. **First public release:** Google does not offer percentage staged rollout for an initial publication. Limit approved launch countries appropriately, use internal/closed tracks first and review managed-publishing timing. Do not describe a first release as a1% staged update.
7. **Subsequent updates:** proposed reviewed stages are5%,25%,50%,100%, with at least24–48 hours and sufficient meaningful usage at each stage. These are an internal proposal, not an automated schedule or guarantee of adequate sample size. Check crash/ANR, cold-start/map/search/routing errors, GPS quality, sustained false safety alerts, deletion failures and backend/provider cost saturation. Do not fabricate reliability or congestion metrics from a few testers.
8. Halt advancement immediately for a known-as-unknown data failure, unverified-as-confirmed marker, sustained bogus overspeed warning, deletion/security failure, critical crash or unavailable production backend. Halt in Play, investigate/disable affected features safely, and prepare a reviewed higher-versionCode fix. A halt does not uninstall already delivered versions; never promise a lower-version rollback. Resume/increase only after evidence and owner approval.

Record owner, reviewers, countries, track, build ID, versionCode, commit, hash, start/stop times in Africa/Accra, actual observations and decisions. Never attach private travel histories or credentials to public GitHub issues/releases.

Sources: [Play testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465), [staged rollout limitations](https://support.google.com/googleplay/android-developer/answer/6346149), [prepare a release](https://support.google.com/googleplay/android-developer/answer/9859348).
